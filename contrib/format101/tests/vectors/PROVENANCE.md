# Compatibility corpus provenance

This directory is the checked-in compatibility corpus used by the Python and Java
encoder verifiers. The expected HPK files are reference outputs; normal verification
does not regenerate them.

## Generation and verification

Expected outputs were generated on Windows with the checked-in `teste_hc_TW.exe`
reference encoder. Generation is deliberately separate from verification:

```powershell
uv run --project python python tests/harness/generate_expected_hpk_windows.py --dir tests/vectors
```

The deterministic generator source is `tests/harness/generate_vectors.py`. For a
generated campaign, record its mode, count, seed, output directory, reference asset
hashes, and the generator source revision alongside the campaign. The current
checked-in corpus predates the generator campaign and has no generator seed.

## Quantization boundary campaign

The `boundaries/` subdirectory contains seventeen deterministic inputs generated by
`tests/harness/generate_boundary_vectors.py`. The checked-in expected outputs were
generated with the Linux `reference/bin/teste_hc_TW_64` binary using:

```bash
PYTHONPATH=python/src python3 tests/harness/generate_boundary_vectors.py
PYTHONPATH=python/src python3 tests/harness/generate_expected_hpk_linux.py \
  --dir tests/vectors/boundaries
```

The campaign covers values just below, exactly at, and just above a half-unit SOG
boundary, SOG clamping below and above its representable range, and half-unit or
clamping boundaries involving temperature, latitude, and pressure offsets. The
native encoder produced output for all seventeen cases. Java and Python now match all
nine outputs; Python uses Java-compatible `Math.round()` semantics, including
rounding an exact positive half-unit upward.

The boundary corpus also covers latitude `-90..90`, longitude `-180..180`, air
temperature `223.15..325.35 K`, course `0..360 degrees`, pressure clamping, and
station identifiers from one to seven characters. The original and group campaigns
provide the one-character and seven-character identifier cases; the boundary names
also exercise six-character identifiers.

## Group-combination campaign

The `groups/` subdirectory contains eight deterministic inputs generated with
`generate_vectors.py --mode combo --per-combo 1 --seed 20261027`. They cover all
visual, wave, and ice marker combinations (`000` through `111`). Marker-zero groups
have their fields missing; marker-one groups contain a mixture of present and
missing fields. The campaign also carries the legacy `001199` value of `1`, and its
outputs exercise the variable-length group layout and final 6-bit/byte padding.

Linux-native expected outputs were generated with:

```bash
PYTHONPATH=python/src python3 tests/harness/generate_expected_hpk_linux.py \
  --dir tests/vectors/groups
```

Both Python and Java match all eight outputs. The `001199` ambiguity remains covered
by these vectors and the original minimal vectors; its meaning is documented in
[`known-limitations.md`](../../docs/known-limitations.md).

## Application-preparation campaign

The `application/` subdirectory contains two sanitized captures produced by
TurboWin's existing `FORMAT_101.write_input_for_101_compression()` method:

| Input vector | Preparation scenario |
| --- | --- |
| `manual_preparation_idMAN001` | Manual observation with a fixed position, heading, relative wind, temperatures, pressure, and date; APR speed is missing. |
| `automatic_apr_preparation_idAPR001` | Automatic/APR observation using the legacy `SOG_APR = 10.0` input, which produces `5.144 m/s` in the prepared file, with the same sanitized environmental values. |

The position is `12°03′N, 45°06′E`; the date is 2026-10-27 12:00 UTC. The
captures are synthetic and contain no operational station or observer data. They
were generated outside the application UI by initializing the same static
preparation fields used by the production method, then copying its generated
`format_101.txt` file. This keeps the fixtures focused on the preparation
contract while avoiding personal or operational data.

Expected outputs were generated with the Linux native reference encoder:

```bash
PYTHONPATH=python/src python3 tests/harness/generate_expected_hpk_linux.py \
  --dir tests/vectors/application
```

Java matches both native outputs exactly. Python currently differs from the
native output at one encoded byte in each fixture; this is recorded as an open
compatibility issue and is not hidden by excluding the application vectors.

Run the checked-in corpus without changing expected files:

```bash
PYTHONPATH=python/src python3 tests/harness/verify_python_encoder_against_vectors.py
python3 tests/harness/verify_java_encoder_against_vectors.py --build
```

On Windows, the same verifier commands use `python` and the Windows Gradle wrapper;
the CI workflow also runs the native reference verification.
